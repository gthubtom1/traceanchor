# 版本维护与发布验收门

## 1. 当前状态

**TraceAnchor 0.1.1 的发布状态由实际资格与发布回执决定。** 用户已启用实施交接修订2的产品实施/发布授权，但发布仍须通过验收门；授权不是验收结果。各发布阶段实际状态以 release-verification.json 为准。

阶段性 144 项测试、后来修复的专项回归、demo 有限通过、打包成功都不是整个 Goal 完成。本地已生成 [qualification.json](qualification.json)，绑定实际候选内容及测试环境，并保存 [安装维护实测](install-qualification.json)；这些记录不替代公开检查和远程门。公共 URL 仅在实际创建/核对后写入发布记录，不使用臆造下载地址。

依据：[实施契约](IMPLEMENTATION-CONTRACT.md) 的 A01–A20 及已启用交接合同的最终完成标准。被冻结的验收项不得为赶发布而删除、降级或改成无效断言。未支持领域可以公开列界限，但承诺范围内的阻断缺陷不能仅靠改文档消除。

## 2. 本地门：按顺序留下真实证据

为什么：包能安装、一个例子能跑和完整可维护产品是不同结论。

1. **需求与来源完整性**：交接修订2的多任务/多目标、可观测性、证据换路、原件/派生/候选隔离、开发子任务均有映射；冻结要求/延后范围/理由明确。原研究快照不改写，必要来源摘要可由固定提交及锚点复核。
2. **真实功能闭环**：不是全靠 mock。自建材料实际走分析→参考证据→有限规格→独立错误候选→差异→修复→新身份重验。负数/错误/边界/状态序列及五维判断分别有断言，visual 非适用有冻结理由。
3. **状态与有效期**：来源/候选/规格/fixture/工具/环境/比较器变化正确失效；不能把旧 pass 用于新输入。记录历史、事务/版本冲突、未知项、子任务父级失效均受测。
4. **资源与失败**：真实超时、取消、输出限制、非法输入/编码、非零业务退出、子孙进程、进程所有权、清理、中断恢复、无进展、HTTP 与进程共同预算。完整清理与 unknown 分开，不能静默重放副作用。
5. **存储与恢复**：L1 不自动删，L2 验收归档门，L3 引用/租约/pin/共享保护；预览/实际删除/中断/并发/越界/链接/磁盘不足均有真实有效断言。数据库检查点、离线 restore、损坏/较新 schema 拒绝及回退分开验证。
6. **接口与宿主**：真实 stdio initialize/list/call/error/cancel/EOF 与 stub 测试分开。官方来源静态配置核对、临时项目真实接线事务和真实宿主模型工作流分别记录；未运行的宿主部分标 not-run，不假装宿主齐全。
7. **安装旅程**：从实际候选 wheel/源码在隔离环境安装，doctor、init、实际 demo/call、配置适用重装、升级/卸载/迁移/回退可复现。默认保留业务资产。同机新虚拟环境准确称为隔离环境，不称全新机器。
8. **文档与维护**：陌生用户可按 README 运行；命令与实际 CLI/API 同步；容量统计/非沙箱/有限验收边界明确。来源机制映射、决策、notices、未来复评交接和适用许可完整。
9. **简单基线评估**：正确性/恢复/重复操作/磁盘/资源/开销有适用的确定性基线；未跑的效果实验明确未跑，不调用无预算付费模型，不作优越性声明。

任一修复触及冻结候选内容后，重跑受影响测试及关键整合门；旧结果不能自动替新包背书。具体 pass/fail/skip/not-run 必须逐项映射，测试数量只作计数。

## 3. 资格记录应包含什么

为什么：未来用户需要知道哪个包、哪个环境、哪条证据支撑支持声明，而不是只有一个总分。

维护者生成的 docs/qualification.json 至少应表达以下信息；这是记录要求，不宣称当前已经存在某个固定 JSON schema：

- product/version、候选内容身份、构建时间与 wheel/sdist SHA-256；明确资格证据与最终制品的绑定方式，避免把互相包含的文件哈希当无限递归要求。
- 测试命令、时间、Python/OS/架构（不含账户、机器名、私人绝对路径）、退出码及可公开结果摘要。
- A01–A20 对应证据、实际断言和通过/失败/跳过/未运行；阻断项及剩余未知。
- mock/stub、真实核心/协议/工具集成、静态配置核对、真实指定宿主工作流分层；未实测平台明确 experimental/not-run。
- 有限 fixture、比较义务、负控和适用边界；不是把 demo 通过写成所有领域通过。
- 安装/重装/升级/卸载/迁移/数据库回退的实际版本与路径类别，业务资产保留断言。
- 性能/效果基线、样本、资源计量与未执行付费模型实验；不借测试数证明优越性。
- 公开检查、包检查、源码/制品一致性和远程发布各阶段状态。

机器可读记录不替代人工看失败输出；故障重试保留先前失败事实。仅建立 CI 配置不写 CI passed。

## 4. 公开文件与制品门

为什么：运行工作区能帮助维护，但通常不适合分发。

- 产品源码、五份使用文档、测试、自建适宜示例、清洁配置模板、许可与来源谱系可进入候选集合；实际集合必须列清。
- 排除 .validation、虚拟环境、__pycache__/pyc、缓存、临时样本、运行工作区/数据库、宿主回执及原配置备份、凭据/环境变量、私人路径/账户/机器信息、真实目标、非公开证据、完整上游快照及许可未清资产。
- 不只看当前工作树，还检查拟发布 Git 历史、wheel、sdist 及归档清单；旧提交内的秘密不会因末次删除自动消失。
- 源码、安装包、包含的 docs/skills/谱系版本一致；自定义构建后端无需第三方构建/运行依赖不代表包已经审查通过。
- 文件名/路径/内容中都检查隐私；链接只用适宜公开固定来源、产品内相对路径或实际已核验地址。
- 保留适用 LICENSE/归属；机制学习与复制分发明确区分。嵌套资产不默认被根许可覆盖。
- 产物有校验值，隔离环境实际从该产物安装并跑有意义命令；后续文档/代码变化后重新打包，不发布陈旧 wheel。

文档引用未来 qualification/requirements-map 不等于文件已存在；发布前确保契约要求的映射和资格产物实际生成、链接有效且内容不含私人路径。

## 5. 远程门与完成状态

为什么：本地完成、远程仓库存在、CI 通过和 Release 下载验证不是同一事件。

只有本地阻断门通过且公开检查完成后，主维护流程才按用户已给授权核对账户权限、选不与上游混淆的名称、创建新仓库、提交推送。既有仓库不接管、不覆盖；认证与全局配置保持原状。

逐项记录：权限核对→仓库创建→推送→实际 CI 结果→Release 创建→实际下载→校验/安装/有意义运行。每项保留准确状态/错误，不能用较前步骤推导后步骤成功。当前文档没有占位远程地址可当真实获取入口。

硬阻塞时完成仍可做的本地事项，保存恢复点和最短下一步，状态为候选/部分完成/阻塞；没有全部达成最终门，不写完整 Goal 已完成。远程错误不是删除测试、忽略本地缺陷或改变目标的理由。

## 6. 版本、兼容与独立维护

- 初始目标版本为 0.1.1。候选状态由资格/发布记录表达，不因 Python 元数据已有版本号就称正式稳定。
- 0.x 不承诺永久 schema/API 兼容。任何破坏性变更必须列影响、迁移、备份/回退、重新验收要求；不能静默改写旧历史或提升导入证据可信度。
- 新 schema 由显式受测迁移进入；旧包遇不兼容版本拒绝写入。不得让用户强改 user_version 作为支持路径。
- 程序、宿主接线、业务数据独立升级/卸载。维护命令与具体版本及资格绑定，业务项目和 L1 默认保留。
- 当前没有长期支持周期、补丁 SLA、自动更新或后台上游抓取承诺；维护状态以后在真实发布记录更新。
- 独立演进，不承担跟随四方上游/API 兼容/自动合并义务。未来复评按 [谱系](provenance/README.md) 和 [交接提示词](../UPSTREAM-REVIEW-PROMPT.md) 固定新基线、保留旧结论、先研究建议；实施以该次任务授权为准。
- 没有明确额外预算不新增产品内付费模型循环。无受控效果评测不称优于上游；工程可用、有限行为正确与效果收益分别披露。

安装与回退步骤见 [storage-maintenance.md](storage-maintenance.md)，平台/宿主边界见 [support.md](support.md)。
